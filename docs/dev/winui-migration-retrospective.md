# WinUI 3 迁移复盘（已暂停）

2026-10-18 起尝试把界面从 WPF 迁移到 WinUI 3 + Composition，2026-10-24 决定暂停，工作重心回到 WPF 版。重构分支 `features/20261018_winui3-rewrite` 保留不删，以后需要时可以从它继续。本文记录做了什么、为什么停、学到了什么，供以后再考虑换界面框架时参考。

## 一、当初为什么迁移

选型原型（`artifacts/architecture-prototypes`，不随 Git 交付）想验证的是「每屏一个宿主窗口，分区、标签、背景都是宿主里的视觉对象」：

- **少窗口、少钩子**：WPF 版每个分区、每块背景都是一个独立窗口，空白处点击穿透靠低级鼠标钩子；新架构用 `SetWindowRgn` 维护可点区域，区域之外直接交给桌面。
- **资源开销更低**：验收标准里写的是「4K 150% 下整屏透明窗口的内存 < 现有图标层（约 30 MB）」，期望整体内存下降（用户反馈过内存偏高）。
- **拖动更跟手**：Composition 动画和合成，期望拖动分区时文字、背景不再落后。

## 二、做到了哪一步

- 6 天里 20 个提交，改动 97 个文件、新增约 1.1 万行；抽出了与界面无关的 `MyDesktop.Core` 工程和 43 项回归检查，搭了不切换桌面的隔离 UI 验证（`MyDesktop.WinUI.Smoke`）。
- 已迁移：真实分区与标签组、Shell 图标、映射目录、四向收起与悬停展开、桌面接管与恢复进程、散放图标、共享选择、复制剪切粘贴删除、改名、拖放、框选、分区移动和调整大小、标签合并排序拆分、完整系统右键菜单。
- 未迁移：设置窗口、托盘、新建和删除分区、标题菜单、列表和详细信息视图、搜索、一键整理、飞行动画、自动更新、备份恢复入口、多显示器等，`docs/TODO.md` 里还有约 37 项。
- 安装包只能打测试包，正式发行一直是 WPF 入口。

## 三、为什么暂停

2026-10-24 用同一台电脑、同一份配置（5 个分区、63 个图标、4K 150%）对比：

| | WPF 1.5.0 | WinUI 测试版 |
|---|---|---|
| 主进程私有内存 | 95–98 MB | 163 MB |
| 主进程工作集 | 178–185 MB | 239 MB |
| 另需的恢复进程 | 无 | 私有 6 MB，工作集 25 MB |
| 安装包 | 2.4 MB | 20.1 MB（已去掉 AI 等组件，原为 39.9 MB） |
| 拖动跟手（实机体感） | 更跟手 | 不如旧版 |

WPF 的数据取自程序启动 1 分钟后自己记的日志，WinUI 是运行 4 分钟后的进程实测、连续 4 次采样一致。

- **两个核心目标都没达到**：功能还缺一大半，内存已经多出约 70%；拖动跟手在原型阶段就没通过验收（见下文），正式迁移后实机体感仍不如旧版。
- **多出来的主要是框架的固定开销**：XAML 框架、Windows App SDK 运行时、Composition 及其依赖，自己的代码优化很难压下去。
- **原生感变差**：默认的 Fluent 控件、对话框式的改名卡片、默认浅色的 Win32 菜单（后来补上了深浅色）都不像系统桌面；WPF 版用的就是 Win32 菜单和原地改名，本来就接近原生。
- **剩下的工作量大**：已迁移的部分还要按原生风格重做界面，未迁移的约 37 项里有设置窗口、搜索、整理这些大块。

## 四、经验教训

1. **先验证动机，再大规模迁移。** 原型阶段拖动延迟已经没通过验收（2026-10-18 实机反馈「整块分区都不跟手，边框也有滞后」），当时决定「暂缓此项优化，继续主线可行性验证」，结果最关键的收益到最后也没兑现。以后换框架，要把迁移的理由列成可测的验收标准，原型阶段不通过就停，不要带着未解决的核心问题进入正式迁移。
2. **内存要测整个进程，不能只测一个窗口。** 原型的验收标准只比较「整屏透明窗口」和「现有图标层」，没算框架运行时本身的开销；换框架前应该先用最小可运行版本测整个进程的私有内存和工作集，和现有版本同配置对比。
3. **框架解决不了真正难的部分。** 桌面接管、窗口层级、点击穿透、Shell 右键菜单、剪贴板、文件拖放、改名，靠的都是 Win32 和 Shell 接口，两个框架都要自己写；WinUI 这边还多了不少要绕开的坑（透明窗口黑边、输入法窗口层级、亚克力背景断开时原生崩溃等，见重构分支的 `docs/dev/winui-migration.md`）。框架只替换了画界面的那一层。
4. **隔离验证覆盖不到真实输入。** 隔离 UI 验证直接调用布局和拖放入口，测不到真实的鼠标手势：散放图标用的是按钮，按钮按下时捕获指针，导致 `CanDrag` 用鼠标时完全不起作用，直到实机才发现；剪贴板被其他程序占用时直接报「拒绝访问」也是实机才遇到。核心交互要尽早实机试。
5. **两套入口并行，修复要做两遍。** 迁移期间 WPF 版照常发了 1.4.0 到 1.5.0，每个修复、每个新行为都要另记一条 WinUI 待办；迁移拖得越久，欠账越多。
6. **默认依赖要逐项审视。** `Microsoft.WindowsAppSDK` 总包会带上 AI、机器学习（onnxruntime、DirectML）、搜索、小组件等用不到的组件，发布产物 153 MB；只引用用到的组件包、只留中英文资源后降到 90 MB。即便如此，安装包仍是 WPF 版的 8 倍。

## 五、留下的东西

- **重构分支**：`features/20261018_winui3-rewrite` 保留，暂停前合过 `main`（到 1.5.0）；它自己的文档在 `docs/dev/winui-migration.md`、`docs/TODO.md`。
- **迁移中发现、WPF 版已经修掉的问题**：从 PeaZip 拖文件要在松手时重新读文件列表（1.4.2）；WPF 用 WPF 自带的剪贴板接口，内部本来就会重试，不受剪贴板被占用的影响。
- **没有搬回 `main` 的**：`MyDesktop.Core` 和 43 项回归检查。其中从 WPF 原样挪过去的模型、配置存储、备份、使用记录、拼音、标签组，`main` 上本来就有；其余选择、几何、收起、布局、改名、拖放规则是专为 WinUI 写的，WPF 有自己的实现。将来想给 `main` 加自动化测试，可以只挑配置保存与迁移、标签组这几块单独搬。

## 六、什么情况下可以重新考虑

- Windows App SDK 的进程固定开销明显下降，或者能和系统共享运行时、安装包不再大出一个量级；
- 出现 WPF 做不到、而用户确实需要的能力；
- 重新开始前，先用最小版本实测内存和拖动延迟，与当时的 WPF 版同配置对比，两项都明显更好再继续。
